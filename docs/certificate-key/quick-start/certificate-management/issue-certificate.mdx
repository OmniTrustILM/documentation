# Issue Certificate

The `RA Profile` serves as a single point of the particular certificate management service. The `RA Profile` is used to perform operations on top of the certificates.

This page covers immediate issuance — the **Request now** request type. The Add Certificate form also offers **Pre-register**, which registers a certificate to be issued later using a challenge secret. See [Register Certificate](./register-certificate.mdx) for that flow.

## Issue new certificate using the API

New `Certificate` can be issued using the `Client Operations` API. There may be some `Attributes` associated with the issuance of the `Certificate`. These `Attributes` represent requirements of some certification authority technology. We can get the list of `Attributes` for issuing of the `Certificate` using the following request:
```bash
curl -X GET \
  --cacert [ca-cert] \
  --cert [client-cert] \
  --cert-type [type] \
  -H "Accept: application/json" \
  https://[domain]:[port]/api/v2/operations/authorities/e045a12a-e114-45ed-90b8-bac7e750e803/raProfiles/166b5cf5-63f2-11ec-90d6-0242ac120003/attributes/issue
  #https://[domain]:[port]/api/v2/operations/authorities/{authorityUuid}/raProfiles/{raProfileUuid}/attributes/issue
```

This returns the list of applicable attributes to issue `Certificate` using the `RA Profile` service, such as:
```json
[] // empty array of Attributes
```

Knowing the attributes, we can issue `Certificate`. The endpoint accepts two shapes of the request body:

- **Uploaded CSR** — provide the CSR as `request`. The CSR is validated against the resolved request-attribute set of the `RA Profile`, in strict or lenient mode — see [External CSR validation](../../concept-design/core-components/ra-profile.md#external-csr-validation).
- **Platform-built request** — provide the request-attribute values as `csrAttributes` together with `tokenProfileUuid` and `keyUuid`. The platform builds and signs the CSR from the selected platform key.

The issuance request is accepted and queued; it runs asynchronously, so the response returns only the certificate's `uuid` — the `certificateData` field is left empty and the signed certificate is not returned here:
```json
{
  "certificateData": "",
  "uuid": "1a90cc6c-76e0-48cb-a027-e52a84c071c2"
}
```

Poll the certificate detail for that `uuid` until its state becomes `Issued`, then read the signed certificate from the detail response.

When the profile validates leniently and the uploaded CSR does not comply with the request attributes, the response also carries `requestAttributeWarnings`, a list of messages. The certificate is issued all the same; the warnings are informational. The field is empty when there is nothing to report. See [Warnings under lenient validation](../../concept-design/core-components/ra-profile.md#warnings-under-lenient-validation).

## Upload existing certificate

Upload the existing certificate to the platform.


1. Click **Certificates** in the left menu 
2. Click **Upload Certificate** (upload symbol <span style={{color: '#1473b5',}}><FontAwesomeIcon icon={faUpload} /></span>)
3. Upload the certificate (CRT file)
4. Click **Submit** to upload the certificate to the platform

## Create new certificate

Select the correct `RA Profile` and issue a new `Certificate`:

1. Click **Certificates** in the left menu
2. Click **Add Certificate** (plus symbol <span style={{color: '#1473b5',}}><FontAwesomeIcon icon={faPlus} /></span>)
3. Keep the request type **Request now** — the certificate request is submitted to the authority immediately
4. Select the `RA Profile`: `ADCS-WebServer`
5. Choose the **Key Source**:
    - **External** — upload your own certificate request (CSR file)
    - **Existing Key** — the platform builds and signs the request from a platform key: select the **Token Profile** and the **Key**, and fill the **Signature Attributes** tab. For a hybrid certificate, switch on **Include Alternative Key**, select the **Alternative Token Profile** and **Alternative Key**, and fill the **Alternative Signature Attributes** tab.
6. With **Existing Key**, fill the **Request Attributes** tab — its values define the content of the certificate request
7. Fill the **Connector Attributes** and **Custom Attributes** tabs, if needed
8. Click **Create**

The `Certificate` has been created.

:::info[Request attributes]
The **Request Attributes** tab shows the resolved set for the selected `RA Profile`. The tab title carries a red `*` when any attribute is required. Mapped fields show a badge next to the label — such as `→ Subject CN` — indicating where the value lands in the certificate. See [Request Attribute](../../concept-design/core-components/request-attribute.md) for the concept.
:::

:::note[External CSR validation]
With the **External** key source, the uploaded CSR is validated against the profile's resolved request-attribute set, in strict or lenient mode — see [External CSR validation](../../concept-design/core-components/ra-profile.md#external-csr-validation). Under strict validation, violations appear in the red **Compliance errors** panel on the form and the request is not submitted. Under lenient validation, the request is accepted and the form stays open with the warning **Certificate request accepted with warnings**, listing what does not comply. Click **Open certificate** to continue to the certificate, or **Close**. Warnings are raised for an uploaded CSR only: a request built from an **Existing Key** raises none.
:::
